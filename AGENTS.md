## Инструкции для AI Агентов

Этот файл содержит критически важные инструкции для любого AI-агента или LLM, работающего с этим репозиторием.

### 1. Протокол Инициализации (ОБЯЗАТЕЛЬНО)

**Прежде чем приступать к выполнению любой задачи, вы должны:**

1.  Прочитать `README.md` в корне проекта.
2.  Прочитать **ВСЕ** файлы в директории `docs/`.

> **Почему это важно?** Вы не можете эффективно работать над проектом, не понимая его архитектуру, бизнес-логику и текущий статус, описанные в документации. Не галлюцинируйте о том, как работает код — изучите документацию.

---

### 2. Политика Ведения Документации

**Если вы вносите ЗНАЧИМЫЕ изменения в проект, вы ОБЯЗАНЫ обновить документацию.**

**Что считается значимым изменением:**
*   Изменение глобального User Flow (пользовательского пути).
*   Изменение архитектуры приложения.
*   Добавление новых ключевых модулей или сервисов.
*   Изменение контрактов API или структур данных, описанных в документах.
*   Логические изменения, влияющие на бизнес-правила.

**Что НЕ требует обязательного обновления docs/ (если не затрагивает суть):**
*   Простой рефакторинг кода без изменения логики.
*   Добавление рядовых библиотек/зависимостей.
*   Исправление мелких багов.

**Ваши действия:**
1.  После внесения изменений проверьте, соответствуют ли файлы в `docs/` новой реальности.
2.  Если нет — отредактируйте их в том же Pull Request / коммите.

---

### 3. Базовые принципы (Core Principles)

1.  **Documentation-First Development** — *каждая* сессия начинается с чтения всех файлов в папке `docs/` (`product.md`, `tech.md`). Не начинай писать код, пока не поймешь текущую архитектуру и задачу.
2.  **Instruction-First** — Для простых задач следуй инструкциям человека напрямую. Для сложных задач — сначала планируй.
3.  **Keep It Simple (MVP)** — Мы делаем MVP. Избегай оверинжиниринга. Используй простые и понятные решения, соответствующие стеку (`aiogram`, `Tortoise ORM`, `SQLite`).

---

### 4. Режим планирования (Plan Mode)

**Когда использовать:**
Задача считается сложной (и требует плана), если затрагивает:
*   Множество модулей (например, handlers + database + services).
*   Новые интеграции (внешние API).
*   Изменение схемы БД (миграции).
*   Архитектурные изменения.
*   Если есть сомнения — считай задачу сложной.

**Процесс:**
Для сложных задач используется папка `plans/`.

1.  Создай файл плана с именем в формате: `plans/NNN-objective.md` (где NNN — инкрементальный номер, например `001-initial-setup.md`).
2.  Файл должен содержать:
    *   **Цель (Objective):** Что нужно сделать (дословно из запроса).
    *   **Шаги (Proposed Steps):** Нумерованный список конкретных действий.
    *   **Риски:** Возможные проблемы.
    *   **Стратегия отката:** Что делать, если все пойдет не так.

**Правило:** Агент **не начинает** реализацию сложной задачи, пока человек не утвердит план (словом "Ок", "Принято" или 👍).

### 5. Система памяти AICODE (Context Anchors)

Эта система **критически важна** для сохранения контекста между сессиями. Агенты имеют ограниченную память, поэтому вы ОБЯЗАНЫ оставлять "хлебные крошки" прямо в коде.

**Правило:** Если вы принимаете неочевидное решение, оставляете недоделку или видите потенциальную проблему — **вы обязаны** оставить соответствующий AICODE-комментарий.

Используйте формат: `# AICODE-<ТИП>: <сообщение>`

#### Типы анкоров:
1.  `AICODE-NOTE:` — **Архитектурное решение.** Объясните, *почему* сделано именно так.
    *   *Пример:* "Используем здесь polling вместо webhook, так как на dev-среде нет белого IP."
    *   *Когда писать:* При выборе неочевидного алгоритма, использовании "хаков" или временных решений.
2.  `AICODE-TODO:` — **Технический долг.** Что нужно сделать, но не сейчас.
    *   *Пример:* "Нет валидации входящего JSON, добавить позже."
    *   *Когда писать:* При использовании `pass`, заглушек (stub), хардкода, отсутствии обработки edge-cases или отсутствии тестов.
    *   **Rule of Thumb:** Если вы пишете код для MVP, задайте себе вопрос: *"Что сломается или будет неудобно, если это выкатить на 10 000 пользователей?"* Если ответ есть (нет кнопки отмены, нет лимитов на ввод, хардкод текстов) — **обязательно** ставьте `AICODE-TODO`.
3.  `AICODE-QUESTION:` — **Блокер/Вопрос.**
    *   *Пример:* "Неясно, как обрабатывать отмену подписки. Уточнить у PM."

#### Пример использования в коде:
```python
# AICODE-NOTE: Используем глобальную переменную для кэша ради MVP.
# В продакшене заменить на Redis.
user_cache = {}

async def get_user(user_id):
    # AICODE-TODO: Добавить обработку ошибок сети
    if user_id in user_cache:
        return user_cache[user_id]
```

### 6. Технические правила (Vibe-Coding Style)

1.  **Стек:** Python 3.11+, aiogram 3.x, Tortoise ORM, SQLite.
2.  **Асинхронность:** Весь I/O (база данных, запросы к Telegram) должен быть асинхронным (`async`/`await`).
3.  **Структура:** Строго следуй структуре папок, описанной в `docs/tech.md`. Не создавай файлы в корне, если им место в `handlers/` или `services/`.
4.  **Безопасность:** Токены только в `.env`. Никогда не хардкодь секреты.

### 7. Самопроверка перед завершением

Перед тем как сказать "Готово", проверь себя:
1.  [ ] Код соответствует задаче?
2.  [ ] Если был план — выполнены ли запланированные на этот этап шаги?
3.  [ ] **AICODE:** Оставлены ли комментарии (`NOTE` для хаков, `TODO` для недоделок) в местах, где код несовершенен?
4.  [ ] Документация (`docs/`) обновлена, если что-то изменилось?
5.  [ ] Линтеры не нужны, но код должен выглядеть опрятно (PEP8).
